# Architecture

## プロセス構成

`stream-shougi-board.exe` が次をすべて持ちます。

```text
stream-shougi-board.exe
├─ main thread: タスクトレイのメッセージループ (Windows のみ)
└─ server thread: tokio runtime
      ├─ hub: 正規の盤面 + 持ち駒 + 表示設定 + 履歴
      │     └─ app/src/session.rs の reducer で全コマンドを直列に適用
      └─ axum: 127.0.0.1 の HTTP と /ws
            ├─ 静的アセット (rust-embed で exe へ埋め込み)
            └─ WebSocket 購読者 (tokio broadcast)

           ▲ command                     │ snapshot
           │                             ▼
   操作画面 (/)                    OBS ブラウザソース (/board)
```

## 状態の持ち主

**サーバーが唯一の正規状態を持ちます。** 操作画面はコマンドを送るだけ、盤面ページは受け取って
描くだけです。この形にすると、

- 操作画面を再読み込みしても OBS 側の盤面は消えない
- 操作画面を 2 枚開いても選択状態が割れない
- 配信に映るものと手元に見えるものが、定義上ずれない

盤面・持ち駒・表示設定を合わせても JSON で数 KB にしかならないので、増分イベントは持たず、
**変化のたびに snapshot を丸ごと配ります**。購読者は全置換すればよく、取りこぼしの検出も
差分の再生も要りません。`rev` は順序確認とデバッグのためだけに残しています。

クリックの意味 (選択なのか移動なのか打ち込みなのか) を決めるのも、クライアントではなく
`app/src/session.rs` です。ここを線の向こう側に置いたので、操作画面が複数あっても解釈が
1 つに定まり、挙動をブラウザ無しで `bun test` から確かめられます。

## ワークスペース

| | 責務 |
| --- | --- |
| `app/` | 盤面モデル、SFEN、コマンド reducer、プロトコル、loopback サーバー、設定、タスクトレイ |
| `client/` | 操作画面と盤面ページ。SVG の描画器は 2 つのページで共有する |
| `protocol-fixtures/` | Rust が書き出し client のテストが読む snapshot。両側のずれを検出する |

クライアントは盤面ロジックを持ちません。`client/src/shogi.ts` は表示側の型と純粋な補助関数だけ、
`client/src/protocol.ts` は `app/src/protocol.rs` の写しです。プロトコルを変えたときは
`protocol-fixtures/snapshot.json` を作り直し、両側のテストが通ることで整合を担保します。

`client/src/Board/component.tsx` は操作画面と盤面ページの両方で、**同じ view 設定のまま**
描かれます。手元のプレビューがそのまま OBS の出力になり、別々に調整する必要がありません。

## 駒の描画

駒は SVG で描きます。五角形のパスに漢字を載せるだけなので、画像アセットを持ち込まずに済み、
OBS 側で盤を大きくしても輪郭が崩れません。成駒は赤字で、成銀・成桂・成香は駒に彫られる
1 文字 (全・圭・杏) を使います。

盤上の駒と持ち駒は 1 つの `<g>` へ id 順に並べます。駒が盤と駒台を行き来しても親が変わらないので、
駒を取って駒台へ飛ばす動きまで CSS transition ひとつで繋がります。この id は SFEN には現れないので、
SFEN を読み込むと振り直されます (局面ごと入れ替わったのだから、それが正しい)。

## Web assets

`client/bin/build.ts` が 2 ページ分の HTML・CSS・JS と、生成済みの第三者ライセンスページを
`client/static/` へ出します。Rust 側は `rust-embed` でこれを取り込みます。release ビルドでは
exe へ埋め込まれるので配布物は 1 ファイルで済み、debug ビルドでは実行時にディレクトリを読むので
watch 中はページの修正が再起動なしで反映されます。

## タスクトレイ

Win32 を直接使います (`app/src/win/tray.rs`)。画面に出さないメッセージ専用ウィンドウを作り、
`Shell_NotifyIconW` でアイコンを常駐させ、右クリックでポップアップメニューを出します。

tooltip の接続数は 1 秒ごとの `WM_TIMER` でプロセス内の値を読み、変わったときだけ書き換えます。
スレッドをまたぐ通知の仕掛けを増やすより、UI スレッドで atomic を 1 つ読む方が単純だからです。

Windows 以外ではトレイを飛ばしてサーバーだけ起動します。開発と自動テストを Linux で回すためです。

## 実装言語

本体は Rust です。配布する exe に入るものをすべて許諾系ライセンスに保つためで、
JavaScript ランタイムを静的リンクする方式では LGPL-2.1 の JavaScriptCore が
避けられませんでした (単一 exe と再リンク規定は相性が悪い)。
`cargo-about` が検証する範囲で、現在の依存はすべて MIT / Apache-2.0 / BSD / ISC などです。

OBS ブラウザソースが読むページは HTML/JS でなければならないので、`client/` は TypeScript と
React のままです。React は MIT で、バンドルされて exe に入ります。

## 盤の操作をこう決めた理由

配信中に横目で触るものなので、迷わず戻せることを優先しています。

1. **成りと陣営反転を別の操作にした。** ダブルクリック 1 つに両方を兼ねさせると、
   歩 → と → 後手のと → 後手の歩 … と一方向に循環することになり、行き過ぎたときに
   目当ての駒へ戻すまで叩き続けることになります。ダブルクリックを成／不成、
   右クリックを先後反転に分ければ、どちらももう一度押すだけで元へ戻せます。
2. **駒を進めたら手番と手数を進める。** 並べた局面をそのまま指し継いで見せることが
   多いためです。並べ替えのための操作 (駒台への移動、成り、反転) では動かさず、
   手番は操作画面から直接指定もできます。

履歴は SFEN 列ではなく盤面そのもので持ちます。SFEN には駒の id が無く、履歴を戻ったときに
駒の対応が切れてアニメーションが飛んでしまうためです。
